# running_led_test 上板 ILA 波形解读

> 抓取文件：`test/Debugger_capture_2026-09-03T07-25-46.csv`
> 测试程序：`test/running_led_test.dat`
> 平台：小眼睛 SoC（RISC‑V 五级流水核 + JTAG + MMIO LED/UART），PANGO(PDS) DebugCore/Inserter 抓取

---

## 1. 抓取配置

本次 ILA 观测的对象是 SoC 顶层的“逻辑字段调试总线”（`Hfpga_jtag_soc.v:35~52` 中带
`(* PAP_MARK_DEBUG="<0/t?/0>" *)` 标记的线网，经 `Debug_core.v` 引出后由 Inserter 接入
DebugCore）。导出 CSV 中包含 7 个总线、共 224 个通道，每个通道是总线的一个 bit：

| CSV 列 | 含义 | RTL 出处 |
|---|---|---|
| `debug_if_pc[31:0]` | IF 级取指 PC | `Htop.v:347` = `if_pc` |
| `debug_id_pc[31:0]` | ID 级 PC | `Htop.v:348` = `id_pc` |
| `debug_ex_pc[31:0]` | EX 级 PC | `Htop.v:349` = `ex_pc` |
| `debug_mem_pc[31:0]` | MEM 级 PC | `Htop.v:350` = `mem_pc` |
| `debug_wb_pc[31:0]` | WB 级 PC | `Htop.v:351` = `wb_pc` |
| `debug_dmem_addr[31:0]` | 访存地址（EX 的 ALU 结果，`Hexu.v:221 dmem_addr = ex_result`） | `Htop.v:357` |
| `debug_dmem_wdata[31:0]` | 访存写数据 | `Htop.v:358` |

- 采样深度：512 个采样点（Sample Index 0~511）。
- 采样时钟：`cpu_clk`（PLL 输出，工程按 70 MHz 设置，见 `Huart_tx` 的 `CLK_HZ=70_000_000`），
  每个采样点 = 1 个 `cpu_clk` 周期，整窗 ≈ 512 / 70 MHz ≈ **7.3 µs**。
- CSV 中每列的 bit 按 **LSB 在前**排列（`debug_if_pc[0]` 是该 PC 的最低位）。

注意：本次抓取只接了 PC 与 dmem 两组总线，`debug_*_ins`、`debug_ctrl`（valid/stall/flush
位图）、BTB 预测总线等没有接入，因此文档中“阶段是否有停顿”等结论是由 PC 时序推出的推断，
已用“推断”标注。

## 2. 被测程序 running_led_test.dat

14 条 RV32I 指令，从地址 `0x0000_0000` 开始（IMEM 基址）。反汇编如下：

| 地址 | 指令编码 | 汇编 | 含义 |
|---|---|---|---|
| 0x00000000 | `400002b7` | `lui x5, 0x40000` | x5 = 0x4000_0000 |
| 0x00000004 | `20028293` | `addi x5, x5, 0x200` | x5 = 0x4000_0200（LED 寄存器） |
| 0x00000008 | `00100313` | `addi x6, x0, 1` | x6 = 1（流水灯初值） |
| 0x0000000c | `0016eeb7` | `lui x29, 0x16e` | x29 = 0x0016_e000 |
| 0x00000010 | `360e8e93` | `addi x29, x29, 0x360` | x29 = 0x0016_e360 = 1_500_000（延时初值） |
| 0x00000014 | `0062a023` | `sw x6, 0(x5)` | **点亮**：写 LED = x6 |
| 0x00000018 | `000e8393` | `addi x7, x29, 0` | x7 = 延时初值（每档重新装载） |
| 0x0000001c | `fff38393` | `addi x7, x7, -1` | 内层延时：x7-- |
| 0x00000020 | `fe039ee3` | `bne x7, x0, 0x1c` | x7 != 0 回跳 0x1c（**被测热点**） |
| 0x00000024 | `00131313` | `slli x6, x6, 1` | 下一档：x6 <<= 1 |
| 0x00000028 | `01037e13` | `andi x28, x6, 0x10` | x28 = x6 & 0x10（是否出界） |
| 0x0000002c | `fe0e04e3` | `beq x28, x0, 0x14` | 未出界 → 回 0x14 写下一值 |
| 0x00000030 | `00100313` | `addi x6, x0, 1` | 出界 → 重新置 1 |
| 0x00000034 | `fe1ff06f` | `jal x0, 0x14` | → 0x14 继续写 |

程序逻辑：`sw` 把当前 x6 写入 LED，随后 x7 从 1_500_000 递减做软件延时；延时结束后
`x6 <<= 1` 点亮下一位；当溢出到第 5 位（`x6&0x10 != 0`）时复位回 1。
故 LED 状态按 **1 → 2 → 4 → 8 → 1 …** 循环，为 4 位流水灯。

## 3. 波形总体情况

整窗 512 个采样点内，PC 只出现过三个值，且与程序延时循环严格对应：

```
0x1c  addi x7, x7, -1     （延时计数器递减）
0x20  bne  x7, x0, 0x1c   （回跳，延时主体）
0x24  slli x6, x6, 1      （延时退出后才真正执行的下一条）
```

即：**整窗全部落在 running_led_test 的“软件延时循环”内部**，窗口内既没有看到
`sw x6,0(x5)` 的 LED 写（`debug_dmem_addr` 从未等于 `0x40000200`，`dmem_wdata` 恒为 0），
也没有看到流水灯翻转到下一档 —— 这符合该程序“99% 时间都在延时”的特点，
抓取窗口恰好截在某一档 LED 的延时中途。

各阶段 PC 的统计分布：

| 信号 | 0x1c（addi） | 0x20（bne） | 0x24（slli） |
|---|---|---|---|
| `debug_if_pc` | 171 | 170 | **171** |
| `debug_id_pc` | 170 | 342 | 0 |
| `debug_ex_pc` | 171 | 341 | 0 |
| `debug_mem_pc` | 171 | 341 | 0 |
| `debug_wb_pc` | 170 | 342 | 0 |

两个关键事实：

1. **0x24（slli）在 IF 被取了 171 次，但从未进入 ID 及其后各级** → 它是一次次
   被“顺序投机取指、随即冲刷”的指令，永远没有真正执行。
2. **各级中 bne 的驻留拍数约为 addi 的两倍**（0x20 : 0x1c ≈ 2 : 1），每个延时迭代在
   EX/MEM/WB 上呈现“1 拍 addi + 2 拍 bne”的节奏。

## 4. 延时循环的精确周期

以“addi 在 EX 级出现”为循环事件计数（`ex_pc == 0x1c`），共 **171** 次，
首次在 Sample 0、末次在 Sample 510，相邻事件间隔**恒为 3**：

```
事件位置: 0, 3, 6, …, 510   （间隔分布：{3 : 170}）
```

结论（推断）：**每个延时循环迭代恰好占用 3 个 cpu_clk**。
512 个采样内完成 171 次迭代，每次迭代只有 2 条有效指令（1× addi + 1× bne），
因此窗口内稳态 IPC ≈ 2/3 ≈ 0.67。

窗口内 3 拍一迭代的流水节奏（取 Sample 0~5 为例，可对照 1:1 波形表）：

| Sample | IF | ID | EX | MEM | WB | dmem_addr | 备注 |
|---|---|---|---|---|---|---|---|
| 0 | 0x24 | 0x20 | **0x1c** | 0x20 | 0x20 | 0x0001dfb5 | addi 执行，x7 递减到 0x1dfb5 |
| 1 | 0x1c | 0x20 | 0x20 | 0x1c | 0x20 | 0 | addi 传 MEM；IF 重定向回 0x1c |
| 2 | 0x20 | 0x1c | 0x20 | 0x20 | 0x1c | 0 | addi 写回；bne 在 EX 停留 |
| 3 | 0x24 | 0x20 | **0x1c** | 0x20 | 0x20 | 0x0001dfb4 | 下一轮 addi（x7=0x1dfb4） |
| 4 | 0x1c | 0x20 | 0x20 | 0x1c | 0x20 | 0 | 重复 |
| 5 | 0x20 | 0x1c | 0x20 | 0x20 | 0x1c | 0 | 重复 |

### 4.1 为什么每轮要 3 拍？

- `bne` 是**回跳且每次必跳**的条件分支。本设计条件分支不进 BTB
  （`Hidu.v:290` 只对 `jal/jalr` 做 `btb_update_valid`），取指默认按顺序预测
  （`Hifu.v:43 if_predict_next_pc = btb_hit ? btb_target : if_pc_reg + 4`）。
- 因此取到 0x20 后 IFU 每轮都会先顺序投机去取 0x24（slli），等到 ID 级判定
  “跳转且预测错误”（mispredict，flush）后再重定向回 0x1c。0x24 那拍取指即被冲刷
  —— 这正是表 3 中 **0x24 在 IF 出现 171 次、在后面各级出现 0 次**的原因。
- 分支重定向与冲刷使该 bne 在 EX/WB 各占约 2 拍（1 拍真正执行 + 1 拍停顿/重放）。
  于是每轮循环净开销 = addi 1 拍 + bne 2 拍 = **3 拍**（推算：1.5M 迭代延时约等于
  4.5M 个 cpu_clk ≈ 64 ms 每档）。

> 波形本身是对“顺序投机 + 冲刷重定向”行为的直接印证：每轮循环里多取的那条
> fall-through 指令（slli）是白白的取指带宽浪费。若想让延时循环更快，
> 可考虑让 BTB 也学习条件分支（如只学习“反向/跳转”分支）。

## 5. dmem_addr 总线 = 延时计数器 x7

`dmem_addr` 在本设计里是 EX 级的 ALU 结果（`Hexu.v:221 dmem_addr = ex_result`，
并非只对访存指令有效）。因此窗口内它只在 **addi x7,x7,-1 于 EX 级执行的那一拍非零**
（171 拍，与 addi-EX 事件完全重合），值即递减后的 x7：

```
Sample  0 : 0x0001dfb5
Sample 510: 0x0001df0b      （共递减 0xAA = 170 次，每轮 -1）
```

- 该值落在 IMEM/DMEM/MMIO 之外，不是真实访存地址；`dmem_wdata` 全窗为 0，
  `dmem_addr == 0x40000200`（LED）一次也没出现 → 与“窗口内没有实际访存写”一致。
- x7 初值为 0x0016_e360（1_500_000）。抓取起点时 x7 ≈ 0x1dfb6，说明当次延时已进行
  约 (1_500_000 − 122_806) ≈ 137.7 万次迭代（≈ 4.13M 拍 ≈ **59 ms**），抓取时距本档
  结束还剩 ≈ 122_806 × 3 ≈ 368K 拍 ≈ **5.3 ms**——即本次 ILA 截取的正是某一档 LED
  延时的最后 ~123K 次迭代。

## 6. 结论

1. CPU 在板上**运行正常**：取指/译码/执行/写回与 running_led_test 的程序语义一致，
   延时循环稳定收敛（x7 每轮严格 -1，周期严格 3 拍，无乱序/异常）。
2. 抓取窗口落在**软件延时循环内部**（该程序几乎全部时间都在延时），因此没抓到
   LED 写与档位切换；若想观察 LED 写 `sw`/流水灯翻转，应把触发条件设成
   `debug_dmem_addr == 0x4000_0200`（或接上 debug_ctrl 的 `dmem_wen` 位再触发）。
3. 观测到的分支行为：条件回跳分支每轮都被顺序投机到 fall-through（0x24）再冲刷，
   即**分支重定向的代价清晰可见**——与代码中“BTB 不学习条件分支”的实现吻合，
   是 3 拍/迭代低效的直接原因（也是该程序的固有延时来源）。
