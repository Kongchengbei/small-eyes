# 真实 RGB565 帧导出与方向查看

当前工作区仍没有找到本工程实板采集的 RGB565 原始帧或 DDR dump。检索到的
`bsp/**/**/*.bin` 是 CPU 固件镜像，`.dump` 是固件反汇编；`manual/4_IC_datasheet/OV5640/IMG_20210222_140752.jpg`
是资料图片，都不能用来代表本板摄像头输出。当前环境也没有 `/dev/ttyUSB*`、
`/dev/ttyACM*` 或 `/dev/serial/by-id/*` 设备，未发现运行中的串口/JTAG 导出进程。
工程历史 `jtagserver.log` 记录的是过往 Flash 操作，不能作为当前连接证明。

普通 Camera 固件可以通过 UART 打印完成帧地址、若干 RGB565 像素样本和整帧 `sum16`
校验值，但不会发送图像数据；因此这些旧日志不能恢复成可视图像。现在增加了独立
one-shot 导帧固件和 PC 接收脚本，仍须实际构建/烧录并连接摄像头才能取得本板实拍。
没有生成伪造或合成的“实拍图”。

## 导出文件格式

当前 Camera/DMA 配置为 640×480 RGB565，每帧 614400 字节。DVP 接收器把传感器先到
的字节组为 RGB565 像素 `{first_byte, second_byte}`；DMA 将像素字写入 DDR，CPU 以
小端 `uint16_t` 读取并校验。因此对 CPU 导出的原始 DDR 字节文件，解码默认采用
每像素低字节在前。若拿到的文件是由其他工具导出或经过字节交换，使用
`--byte-order big` 对照。紧凑帧默认 stride 为 1280 字节；DDR 1 MiB 槽的帧数据
位于槽首，后续为未定义/未使用空间。若 dump 从 DDR 基址开始且目标帧在非零地址，
需按该帧的 CPU 可见地址减去 dump 起始地址计算 `--offset`。

有真实的紧凑 RGB565 帧文件后运行：

```sh
python3 tools/rgb565_dump_to_png.py cam1.rgb565 cam1_frame
```

默认输出 `cam1_frame_original.png`、`_hflip.png`、`_vflip.png` 和 `_hvflip.png`，
用于比较原始方向与水平/垂直翻转。支持完整 DDR dump 的子区域、stride 及其他尺寸：

```sh
python3 tools/rgb565_dump_to_png.py ddr_dump.bin cam1_frame \
  --width 640 --height 480 --stride 1280 --offset 0x180000
```

这些 PNG 只有在输入真实板端导出数据后才有实拍意义。工具不改变像素方向、也不
应用 Camera 镜像寄存器；默认图就是输入像素的原始行列顺序。图像方向的最终结论
仍需实际帧内容判定。

## 串口 one-shot 导出协议

`tools/capture_rgb565_uart.py` 是电脑端二进制接收器，使用跨平台 pySerial；它不是
固件。完整帧只能由配套的 one-shot 导出固件产生。固件应先正常打印启动/配置文字，
并在开始二进制前打印 `DUMP_READY`；接收器扫描串口文本，找到固定头魔数后才进入
二进制解析。帧协议字段均为 little-endian：

| 偏移 | 长度 | 字段 | 本版本要求 |
|---:|---:|---|---|
| 0 | 8 | magic | ASCII `R565DMP1` |
| 8 | 2 | version | 1 |
| 10 | 2 | header_len | 44 |
| 12 | 1 | camera | 1 (CAM1) |
| 13 | 1 | format | 1 (`RGB565_LE`) |
| 14 | 2 | flags | 1 (CRC32 有效) |
| 16 | 4 | frame_count | DMA 完成帧号 |
| 20 | 4 | frame_addr | 完成 descriptor 的 CPU 可见 DDR 地址 |
| 24 | 2 | width | 640 |
| 26 | 2 | height | 480 |
| 28 | 4 | stride | 1280 bytes |
| 32 | 4 | payload_len | 614400 bytes |
| 36 | 4 | crc32 | payload 的 CRC-32/IEEE |
| 40 | 4 | reserved | 0 |

44 字节头后紧跟恰好 614400 个 RGB565 原始字节，再跟 8 字节 ASCII `END565D1` 和
4 字节 little-endian CRC32。CRC 使用 IEEE/CRC-32/ISO-HDLC（反射多项式
`0xEDB88320`，初值和末值异或均为 `0xFFFFFFFF`），只覆盖 payload；头和 footer 中
的 CRC 必须相同。固件必须在整个帧发送完成前保持该 ready 槽占用，不要在 DMA 仍
可能写帧时读 DDR；推荐在完成 descriptor 后停止采集，确认此前 DDR 写响应排空，
再发头和 payload，传输完成后才释放该槽。二进制阶段必须只发原始协议字节，不能
夹杂日志或经文本 `uart_putc()` 的 CR/LF 转换。

## 电脑端实际操作

### 位流前提

该 one-shot 固件要求当前 FPGA 位流使用 Full DDR profile：
`SOC_CPU_MEM_BRAM=0`、`SOC_ENABLE_DDR=1`、`SOC_ENABLE_CAMERA=1`、
`PREPROCESS_ENABLE=0`。默认 BRAM 位流没有 DDR/Camera；开启前处理时 Camera 使用者
切换为硬件前处理模块，CPU release 会被拒绝，且前处理可能同时读取或归还 raw slot，
因此不满足此诊断程序独占帧槽的前提。不要为此导出步骤直接改写当前配置或烧录位流；
请使用已经支持 DDR+Camera 且关闭前处理的位流。导帧固件会自行配置摄像头为
640×480 VGA RGB565。

固件端已有单独 one-shot 构建目标；普通 `camera_uart_debug` 和
`camera_stereo_app` 固件仍没有完整帧 UART 导出能力。不能只运行接收脚本就从普通
固件得到图像。先按实际接线构建其中一种导出镜像：

```sh
make -C bsp/camera_stereo_app frame-dump-local
# 或：make -C bsp/camera_stereo_app frame-dump-remote
```

产物分别是 `bsp/camera_stereo_app/camera_frame_uart_dump_local.bin` 和
`bsp/camera_stereo_app/camera_frame_uart_dump_remote.bin`，local 使用 FPIOA[0]/C24，
remote 使用 FPIOA[31]/AB26；两个镜像当前均为 16384 字节。按工程现有流程由操作者
选择/烧录匹配的镜像；接收脚本不会烧录。固件先执行普通配置并等待首帧约 20 秒；
失败会在二进制前打印
`DUMP_ERROR code=N`，成功则打印 `DUMP_READY` 并 flush，随后只发二进制帧头、payload、
footer；传输和 flush 完成后才释放刚导出的槽。然后安装 pySerial（如已安装可跳过）：

在菜单配置的 firmware BIN/path 字段选择 local 镜像时，输入下面的字面路径：

```text
bsp/camera_stereo_app/camera_frame_uart_dump_local.bin
```

remote 版本对应路径为 `bsp/camera_stereo_app/camera_frame_uart_dump_remote.bin`。
下划线必须是普通 `_` 字符；不要输入 Markdown 转义形式 `\_`。路径以工程仓库根目录
为基准。

Windows PowerShell：

```powershell
Set-Location F:\SocFpga
py -m pip install pyserial
New-Item -ItemType Directory -Force captures
py tools\capture_rgb565_uart.py COM5 captures\cam1
```

将 `COM5` 换成设备管理器中 CP2102/USB-UART 实际 COM 口。启动命令后等脚本显示正在
等待有效 `R565DMP1` header，再复位/重新上电运行 one-shot 固件。导出镜像必须和板端当前接线/引脚
约束一致：

- local 镜像：FPIOA[0]/C24。
- remote 镜像：FPIOA[31]/AB26。

串口为 115200、8-N-1、无流控。

WSL/Linux 中 USB-UART 已映射为 `/dev/ttyUSB0` 时：

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install pyserial
mkdir -p captures
python tools/capture_rgb565_uart.py /dev/ttyUSB0 captures/cam1
```

把设备名换成实际 `/dev/ttyUSB*` 或 `/dev/ttyACM*`。如果串口仍由 Windows 持有、没有
映射进 WSL，应在 Windows PowerShell 用 `COMn` 命令运行；同一个 COM 口不可同时由两
边打开。要取消可按 Ctrl+C；脚本保留 `.rgb565.incomplete` 和 `.incomplete.json`，
不会命名成可解码的完整 `.rgb565`。未出现完整 header/payload/footer 或 CRC 不符时
同样判失败。默认拒绝覆盖同前缀的输出，换一个输出前缀重试即可。

完整接收并验证后，脚本自动保存 `captures/cam1.rgb565` 和 `captures/cam1.json`，然后
调用本仓库的 `tools/rgb565_dump_to_png.py` 生成 `cam1_original.png`、`cam1_hflip.png`、
`cam1_vflip.png`、`cam1_hvflip.png` 四张方向对照 PNG。115200 baud、
8-N-1 下 614400 字节至少传输约 53.3 秒；one-shot 固件在此期间停止后续采集，
防止 CPU 读帧时 DMA 复用/覆盖缓冲。接收日志、启动文字及 `DUMP_READY` 均在魔数前，
不写进 `.rgb565`。接收器校验 header 的 camera/尺寸/stride/长度/地址，验证 payload
长度、CRC 和 footer；不完整或损坏的数据不会当成有效图像。

`--start-timeout` 默认 180 秒，用于等待启动日志、首帧等待和 header；
`--frame-timeout` 默认 150 秒，覆盖 53.3 秒 payload 理论最短传输时间以及串口分块间隔。
固件错误码 1–7 分别表示相机探测、配置、首帧超时、descriptor 校验、停止/排空超时、
停止后 descriptor 校验、DMA 未停；接收到错误时不会产生完整 `.rgb565`。

PC 接收器已用临时合成协议字节做过软件路径检查：模拟短读、启动文本和非法 magic
候选后扫描到有效 header、固定长度 payload、CRC/footer 校验，以及解码器 PNG 输出链路；
另外确认 CRC 错误和截断流只留下 `.incomplete` 文件，不产生正式 `.rgb565`。这些是
host 工具的软件协议自检，PNG 文件只在临时目录生成并删除，不是摄像头帧或硬件
testbench/实板验证。当前仍无真实板端导出数据，尚未产出实拍 PNG。

pySerial 在 Windows 与 POSIX 使用同一串口 API，带超时读取可能返回少于请求的字节，
接收器因此按总超时循环收齐协议规定的固定长度并显式报错，参见
[pySerial Serial API](https://pyserial.readthedocs.io/en/latest/pyserial_api.html)。
