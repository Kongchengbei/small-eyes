# Camera 处理全链路

## 1\. 16 MiB、Frame Buffer 和缓冲管理是什么关系？

当前地址表 (soc/soc\_addr\_map.vh:30)的规划是：

```
NPU Input 预留区：0xB8000000 ～ 0xB9000000，共 16 MiB

├─ 第 1 MiB：Camera Buffer 0，已使用
├─ 第 2 MiB：Camera Buffer 1，已使用
└─ 后面 14 MiB：当前未纳入 Camera 缓冲管理
```

一帧图像实际需要：

```
640 × 480 × 2 字节 = 614400 字节 ≈ 0.586 MiB
```

因此：

- 按图像实际大小紧密排列，16 MiB 理论上能容纳 **27 帧**。
- 按目前每个槽预留 1 MiB 的方式，能容纳 **16 个槽**。
- 但现在硬件只实现了 **2 个槽**，并没有实现 16 槽或 27 帧的队列。

所以，**预留空间足够，不等于 DMA 已经具备使用全部空间的能力。** 剩余区域可以纳入后续设计，但还要给模型输入、前处理结果等用途安排空间。

## 2\. 当前图像到底经过哪些流程？

当前有三条不同用途的路径：

```
配置：CPU ──SCCB──→ 摄像头

图像：摄像头 → DVP接收 → Async FIFO → Camera DMA
                                         ↓
                                AXI/DDR控制器 → DDR帧缓冲

调试：硬件状态 → MMIO快照 → CPU → UART → PC
```

UART 不在图像搬运路径里。下面逐项解释。

### ① CPU 初始化摄像头：决定摄像头输出什么

CPU 执行 C 程序，通过 SCCB 写摄像头内部寄存器，配置：

- 分辨率：640×480。
- 像素格式：RGB565。
- 时钟、同步信号极性。
- 开始输出图像。

这里 CPU 是在“设置摄像头”，**不是逐字节接收图像**。

你刚修改的 `0x4740=0x20` 就属于这个流程，用来让摄像头输出的同步规则与 FPGA 接收规则一致。

### ② DVP 接收：把摄像头的字节变成像素

摄像头通过这些信号输出数据：

| 信号        | 作用                      |
| ----------- | ------------------------- |
| PCLK        | 告诉 FPGA 什么时候采样    |
| VSYNC       | 提供帧边界                |
| HREF        | 指示一行有效数据          |
| DATA\[7:0\] | 每个采样周期传输 8 位数据 |

RGB565 一个像素是 16 位，当前接口每次只有 8 位，因此 FPGA 将两个字节拼成一个像素。

DVP 模块同时统计行数、像素数，检查字节配对和同步关系，并产生帧开始、行结束、帧结束标记。

**它负责理解摄像头接口，不负责管理 DDR 地址。**

### ③ Async FIFO：跨时钟并吸收短暂等待

摄像头 PCLK 和 DDR 时钟不是同一个时钟，所以不能直接把不断变化的数据接过去。

Async FIFO 的作用是：

- 安全地跨时钟传递像素和边界标记。
- 暂存少量数据，吸收 DDR 短时间不能接收的情况。
- 保持数据顺序。

**它是短暂中转站，不是存几十帧图像的地方。**

因此，FIFO full 与 DDR 缓冲没有空闲槽，是两个不同的问题。你最近的日志中 FIFO 峰值只有 5，没有记录到溢出。

### ④ Camera DMA：自动把像素写入 DDR

Camera DMA 从 FIFO 取出像素，选一个空闲 Frame Buffer，然后连续写入。

当前实现会把 **16 个 RGB565 像素组成 32 字节的 AXI 写数据**，交给 DDR 访问通路。

它还负责：

- 计算写入地址。
- 检查一帧的行数、像素数和字节数。
- 累计简单 checksum。
- 等待 DDR 写响应。
- 完整、无错误地写完后，发布“这一帧可读取”的信息。

**CPU 不需要参与逐像素搬运。**

AXI 桥接、仲裁和 DDR 控制器则负责把这些读写请求落实到 DDR，并协调 Camera 与 CPU 等访问者。

### ⑤ DDR Frame Buffer：保存完整图像，并保护它不被覆盖

Frame Buffer 就是 DDR 中指定的一块地址区域。

目前两个槽轮流使用：

```
Buffer 0 写完 → 保留给消费者读取
Buffer 1 开始写下一帧
```

写完后，DMA 设置对应的 READY 标志。消费者读完后，必须发出 RELEASE，允许这块区域再次被覆盖。

**RELEASE 不清空图像，只改变“这块区域能不能重新写”的权限。**

如果新帧到来时两个槽都没有释放，当前 DMA 会丢弃新帧并记录 `CODE=9`。它不会擅自向第三个地址写，也不会覆盖正在被读取的图像。

### ⑥ 当前 CPU 调试程序：充当测试消费者

现在还没有 AI 消费者，所以 CPU 在代替它验收：

1. 通过 MMIO snapshot 获取一致的完成帧信息。
2. 确认尺寸、地址和槽号有效。
3. 读取少量像素样本。
4. 扫描完整 DDR 图像，重新计算 checksum。
5. 与 DMA 的 checksum 对比。
6. 打印结果，释放缓冲。

你看到 `MATCH=YES`，说明这些已检查帧的 DDR 回读结果与 DMA 累计值一致。

但这个测试消费者比较慢。**它读图和打印期间，缓冲一直被保护着，DMA 不能覆盖。** 这才是当前出现无空闲槽的主要原因。

## 3\. 将来接入 NPU 后，流程会怎样？

目标流程大致是：

```
DDR 原始图像
    ↓
按模型要求进行前处理
    ↓
模型输入数据
    ↓
NPU 读取并计算
    ↓
输出识别结果
```

这里有一个重要区别：

**地址区叫“NPU Input”，并不意味着写进去的 RGB565 图像已经是模型能直接使用的输入。**

具体模型可能需要缩放、颜色格式转换、量化或数据布局调整。这部分接口还没有在当前 Camera 链路中完成。

缓冲什么时候释放，要看谁最后读取它：

- 如果 NPU 直接读取原始图像，就等 NPU 读完再释放。
- 如果前处理把结果存入另一个区域，原始图像在前处理读完后就可以释放，不必等待整个推理结束。
