# CPU 优化方向汇总

更新日期：2026-10-13。当前工作基于 menuconfig 的 BRAM 配置，CPU 70 MHz，保持 IF→ID→EX→MEM→WB 五级流水线。

## 目标与边界

主要目标：减少相同程序的执行拍数，提高固定频率下的 CoreMark/MHz。允许为性能合理增加 LUT，记录 CoreMark/LUT，但不把压低 LUT 当作当前首要目标。

优化面向通用指令执行、数据依赖、乘除法和控制流。CoreMark 用于评估收益，不依据它的固定地址、常量、输入或特定程序片段增加专用捷径。

DDR 和 BRAM 是 menuconfig 明确支持的配置。CPU 修改收益按同配置比较；DDR 作为兼容性验证配置。临时关闭外设按用户转述的赛事要求执行。

## 已实现的工作

| 工作 | 作用 | 状态 |
| --- | --- | --- |
| 除法完成当拍放行 | 取消结果已有效后的额外 EX 完成状态等待 | 已实现并实板验证 |
| MEM→EX 前递 | 允许紧邻 load 的后继在 EX 获取结果，减少 ID 气泡 | 已实现并实板验证 |
| 前递范围扩展 | 覆盖 ALU、load/store 地址、store 数据、M 操作数和 CSR 寄存器源 | 已实现并实板验证 |
| 操作数就绪与结果保存 | 操作数有效后启动计算或访存；背压下保存前递值 | 已实现并验证 |
| BRAM 重定向当拍取指 | flush 当拍请求正确目标，缩短恢复等待 | 已实现并实板验证 |
| 连续 BRAM 取指 | 无阻塞时支持每拍交付一条指令 | 已有能力，不计为下一轮新收益 |

分支和 JALR 仍在 ID 使用操作数，其紧邻 load 依赖停顿仍保留。普通乘法仍由 EX 启动，内部两级计算时 EX 原地等待。正常除法仍固定迭代 32 轮。BTB 仍是 16 项直接映射、两位方向计数器。

最初的 ICache/DCache 比较与地址快照修改属于 DDR/Cache 时序候选，不作为当前 BRAM 拍数收益的依据。

## 后续方向与暂定优先级

以下是候选任务，尚未实施。总跑分收益需要执行频度和等待占比支持，不能仅依据单次节省拍数排序。

### 0. 统计当前剩余开销

在现有离线仿真入口统计乘法/除法执行次数及等待拍数、分支/JALR 的 load 依赖停顿、预测错误类型、MEM 响应等待和 IF 空拍。

指令次数与等待拍数分别记录。阻塞原因重叠时按互斥分类统计，避免将同一拍重复相加。CoreMark 作为评估工作负载，统计不应改变生产程序或加入默认启用的 FPGA 硬件计数器。

这项统计决定下一轮应优先减少乘法等待、除法迭代还是控制流气泡。

### 1. 乘法提前启动

位置：`cpu/Hidu.v`、`cpu/Htop.v`、`cpu/Hexu.v`、`cpu/mul.v`。

现在：ID 发射 → 进入 EX → 第一阶段部分积 → 第二阶段合并 → 进入 MEM。

候选：在 ID 确认发射且两个操作数均就绪时启动部分积，进入 EX 时第一阶段已经完成，争取每条满足条件的乘法少等一拍。

沿用现有乘法资源和四种 RV32M 乘法语义。load 结果还未就绪的乘法继续使用 EX 启动路径，不能破坏第二轮已实现的 load→M 前递。需要处理发射、结果关联、背压、连续乘法与 flush。

主要代价：ID 操作数/前递到乘法器的组合路径及启动选择逻辑。必须检查 70 MHz 时序；不预先保证所有乘法都能提前启动。

### 2. 改善控制流预测

位置：`cpu/Btb.v`、`cpu/Hifu.v`、`cpu/Hidu.v`、`cpu/Htop.v`。

当前 16 项直接映射 BTB 可能出现分支间替换。先区分容量/索引冲突、方向预测错误和间接目标变化，再选择：

- 扩到 32 或 64 项，减少表项替换。
- 增加返回地址栈，用调用/返回语义预测 `ret` 的目标。
- IF 对直接 JAL 做预译码，提前形成目标，减少首次执行时的重定向损失。

这类优化减少冲刷次数，覆盖条件分支、函数调用和返回。资源可以合理增加，但更大的表和更复杂的 IF 选择可能影响时序。返回地址栈需要正确处理冲刷、溢出、空栈、调用链接寄存器和通用 JALR。

### 3. 除法提前完成与减少迭代

位置：`cpu/div.v`、`cpu/Hexu.v`。

先处理通用可直接求解条件：被除数为零，除数为 ±1，被除数绝对值小于除数绝对值。已有除零和有符号溢出处理保持正确。

随后评估跳过高位无效迭代，或每拍处理两位，将主要迭代数从 32 降到约 16。更少迭代可以减少 EX 对后续指令的阻塞，但组合逻辑更复杂，商/余数及有符号修正需要统一验证。

只有实际 DIV/REM 等待占比较高时，优先投入更复杂的除法器改造。

### 4. 乘法流水化与独立指令重叠

位置：`cpu/Hexu.v`、`cpu/Hmemu.v`、`cpu/Htop.v`、`cpu/mul.v`。

现有乘法器内部有两级计算，但 CPU 将乘法保持在 EX。候选是重新安排结果随指令传递，允许后续独立指令继续执行，提高乘法吞吐。

需要保证依赖者等待、结果前递、结果与 rd 对齐、背压、异常和按顺序提交。作为较大改造，放在前三项之后；不将内部乘法流水化等同于增加整个 CPU 的流水线级数。

## 时序配套工作

最新最差 CPU 路径起于 DMEM 同步读输出，经 MEM 数据处理、EX 操作数选择和 ALU，再进入 ID 控制，最终到 IF PC 寄存器。最差路径为 19 级逻辑，数据路径约 12.939 ns，约 64.2% 是布线延迟。

因此，前递与控制流优化应同时检查跨级组合路径。可以优化选择器结构、load 格式化、store 数据格式化中的串行门控及高扇出控制；此类工作主要用于支持 70 MHz 或增加频率余量，不单独算作 CoreMark/MHz 提升。

当前不优先移动全部分支到 EX：它会改变分支解析时机，可能减少某些 load 依赖等待，也可能增加其他分支的恢复开销，需用整体执行数据权衡。

现在前递已扩展到 M 和访存消费者，结果保存逻辑在 EX 多拍计算及设备背压时有实际用途。之前针对“只有普通 ALU 前递”提出的删除保存逻辑候选，不再直接适用当前结构。

## 验收与工作方式

每轮保存当前稳定 RTL、正式固件及报告基线，记录具体改动与单项原理。先完成用户授权的范围，再统一验证；沿用 Luna high 实现，不新增中间 testbench。

最后使用现有指令入口验证 BRAM 功能、DDR 兼容、MMIO/背压、分支与异常、RV32M 和 CSR。短迭代 CoreMark 用于 CRC 和周期趋势，正式成绩使用原生产固件、3000 次迭代和实板运行。

主要验收：固定 70 MHz，Total ticks 低于当前 1143222397，CRC 正确，CoreMark/MHz 高于 2.62416，时序通过。记录 LUT 与 CoreMark/LUT，允许为执行性能作合理资源交换。整体频率变化另行比较，避免把 MHz 增加算作每 MHz 执行效率改善。
